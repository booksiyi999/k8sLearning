## 1. Requests vs Limits 的区别和用途

### 1.1 核心概念

Kubernetes 中每个容器可以（且应该）为 CPU 和 memory 两种计算资源分别指定 **request** 和 **limit**：

| 属性 | request（请求量） | limit（上限） |
|---|---|---|
| **用途** | 调度依据：kube-scheduler 根据 request 决定 Pod 放到哪个 Node | 运行时限制：kubelet 通过 cgroup 硬限制容器最多能用多少 |
| **谁关心** | kube-scheduler（调度器） | kubelet + 容器运行时 + Linux 内核 |
| **能否超过** | 可以。如果 Node 上有空闲资源，容器可以使用超过 request 的量 | 不可以。超过 limit 会被限制或杀掉 |
| **不设置时** | 如果设了 limit 但没设 request，K8s 自动把 limit 复制为 request | 如果不设 limit，容器可以使用 Node 上所有可用资源 |

### 1.2 调度行为

kube-scheduler 在调度 Pod 时，会检查每个 Node 上 **所有已调度 Pod 的 request 之和** 是否超过该 Node 的容量。注意：

- 调度器只看 request，不看 limit，也不看实际使用量
- 即使 Node 上实际 CPU/内存使用率很低，如果 request 总和超了容量，调度器也会拒绝把 Pod 放到该 Node
- 这是为了防止后续资源使用增加时的争抢

### 1.3 运行时行为

kubelet 启动容器时，会把 request 和 limit 传给容器运行时，后者通过 Linux cgroup 来实现：

- **CPU limit** = 硬上限。每个调度周期内核检查是否超限，超了就 throttle（限流等待）
- **CPU request** = 权重。多个容器竞争 CPU 时，request 大的容器分到更多 CPU 时间
- **Memory limit** = 硬上限。容器尝试分配超过 limit 的内存时，内核 OOM 子系统介入，杀掉容器内进程
- **Memory request** = 主要用于调度。在 cgroup v2 上，容器运行时可能用 request 设置 memory.min/memory.low 提供保护

### 1.4 重要规则

> 如果只设了 limit 但没设 request，Kubernetes 会自动把 limit 的值复制为 request。这意味着该容器会被当成 Guaranteed QoS 处理（见下文）。

## 2. CPU / Memory 单位详解

### 2.1 CPU 单位

| 写法 | 含义 | 等价 |
|---|---|---|
| `1` 或 `1000m` | 1 个 CPU 核心 | 1 物理核 / 1 虚拟核 |
| `500m` 或 `0.5` | 500 millicpu（半核） | 0.5 CPU |
| `250m` | 250 millicpu（四分之一核） | 0.25 CPU |
| `100m` | 100 millicpu | 0.1 CPU |

关键点：

- **m = millicpu / millicores**（毫核），1 CPU = 1000m
- CPU 资源是 **绝对量**，不是相对比例。500m 在单核机和 48 核机上代表相同的算力
- Kubernetes 不允许精度低于 1m（0.001 CPU），建议用 millicpu 形式而非小数形式以避免精度问题
  - `0.5m` 是非法值（低于 1m），但 `0.0005` 不容易一眼看出是非法的

### 2.2 Memory 单位

| 后缀 | 含义 | 类型 | 示例 |
|---|---|---|---|
| `Ki` | Kibibyte = 2^10 = 1024 字节 | 二进制（power-of-two） | `128Mi` = 128 MiB |
| `Mi` | Mebibyte = 2^20 = 1,048,576 字节 | 二进制 | `256Mi` |
| `Gi` | Gibibyte = 2^30 = 1,073,741,824 字节 | 二进制 | `1Gi` |
| `Ti` | Tebibyte = 2^40 | 二进制 | `1Ti` |
| `k` | Kilobyte = 10^3 = 1000 字节 | 十进制（SI） | `128M` = 128 MB |
| `M` | Megabyte = 10^6 | 十进制（SI） | `256M` |
| `G` | Gigabyte = 10^9 | 十进制（SI） | `1G` |
| 纯数字 | 字节 | 无后缀 | `128974848` |

关键点：

- **大小写敏感！** `M` = megabyte（10^6），`m` = millibyte（1/1000 字节）
  - `400m` = 0.4 字节（几乎肯定是你写错了，应该是 `400Mi`）
- 以下写法表示大致相同的内存量：`128974848`、`129e6`、`129M`、`123Mi`
- 生产环境推荐用二进制后缀（Mi, Gi），因为它们和操作系统内存管理对齐

### 2.3 Pod 级别资源

Kubernetes v1.34+ [beta] 支持 Pod 级别资源声明（PodLevelResources feature gate）：

- Pod 的总 request/limit = 所有容器 request/limit 之和
- 也可以直接在 `spec.resources` 下声明 Pod 级别的 CPU/memory 预算
- 适合容器数量多、难以精确评估单个容器资源需求的场景

## 3. Pod QoS（服务质量）等级

Kubernetes 根据容器的 request/limit 配置自动将 Pod 分为三个 QoS 等级：

| QoS 等级 | 判定条件 | 驱逐优先级 | 适用场景 |
|---|---|---|---|
| **Guaranteed** | 每个容器的 CPU 和 memory 的 request 都等于 limit，且都 > 0 | 最低（最后被驱逐） | 生产关键服务、对延迟敏感的工作负载 |
| **Burstable** | 不满足 Guaranteed 条件，但至少有一个容器设了 request 或 limit | 中等 | 一般业务、可以容忍资源波动的服务 |
| **BestEffort** | 所有容器都没有设任何 request 或 limit | 最高（最先被驱逐） | 开发测试、批处理任务 |

### QoS 等级的关键影响

1. **节点资源压力时的驱逐顺序**：BestEffort → Burstable → Guaranteed
2. **CPU 管理策略**：只有 Guaranteed Pod 且 CPU request 为整数时，才能使用 static CPU 管理策略获得独占 CPU
3. **内存 QoS（cgroup v2）**：
   - Burstable Pod：kubelet 设置 `memory.high` 在到达 limit 前做内存限流（默认 throttling factor = 0.9）
   - Guaranteed Pod：request = limit，无需额外限流
   - BestEffort Pod：无内存保护
4. **QoS 等级在 Pod 创建时确定，生命周期内不可变**。如果 in-place resize 导致 QoS 变化，会被拒绝

## 4. 生产环境 Best Practices

### 4.1 基本原则

| 原则 | 说明 |
|---|---|
| **永远设置 request 和 limit** | 不设置 = 无限使用 = 可能拖垮整个 Node |
| **request 和 limit 不要差距过大** | 比如 request=100m, limit=4 会导致调度时算 100m 但运行时可吃到 4 核，容易引起 Node 资源争抢 |
| **关键服务用 Guaranteed** | request = limit，获得最高优先级和独占 CPU 能力 |
| **区分 CPU 和 Memory 的策略** | CPU 是可压缩资源（compressible），Memory 是不可压缩资源（incompressible） |

### 4.2 推荐配置模板

**生产关键服务（Guaranteed QoS）：**
```yaml
resources:
  requests:
    cpu: "1000m"      # 1 核
    memory: "2Gi"
  limits:
    cpu: "1000m"      # = request → Guaranteed
    memory: "2Gi"     # = request → Guaranteed
```

**一般业务（Burstable QoS）：**
```yaml
resources:
  requests:
    cpu: "500m"       # 保底半核
    memory: "512Mi"
  limits:
    cpu: "1000m"      # 最多 1 核（2 倍 request）
    memory: "1Gi"    # 最多 1Gi（2 倍 request）
```

**批处理/低优先级任务（BestEffort 或 Burstable）：**
```yaml
resources:
  requests:
    cpu: "100m"
    memory: "128Mi"
  # 不设 limit 或设很宽松的 limit
```

### 4.3 集群级别管控

| 机制 | 作用 | 作用域 |
|---|---|---|
| **LimitRange** | 设定每个 Pod/Container 的 min/max/default request/default limit | Namespace 级别 |
| **ResourceQuota** | 限制整个 Namespace 的资源总用量 | Namespace 级别 |
| **ValidatingAdmissionPolicy** | 更灵活的策略校验 | 集群级别 |

**LimitRange 示例（强制每个容器有默认值）：**
```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: resource-constraints
spec:
  limits:
  - default:          # 默认 limit
      cpu: "500m"
      memory: "512Mi"
    defaultRequest:   # 默认 request
      cpu: "250m"
      memory: "256Mi"
    max:               # 最大值
      cpu: "2"
      memory: "4Gi"
    min:               # 最小值
      cpu: "100m"
      memory: "128Mi"
    type: Container
```

### 4.4 CPU 管理策略

| 策略 | 说明 | 适用场景 |
|---|---|---|
| `none`（默认） | 使用 CFS quota 限制，CPU 可在不同核之间迁移 | 大多数工作负载 |
| `static` | 为 Guaranteed Pod（整数 CPU request）分配独占 CPU 核 | 对 CPU cache 亲和性和调度延迟敏感的工作负载（如数据库、实时处理） |

启用 static 策略需要修改 kubelet 配置并重启节点。

### 4.5 资源监控与调优

1. **部署 Metrics Server**：`kubectl top pods` 查看实时资源使用
2. **使用 VPA（Vertical Pod Autoscaler）**：自动推荐/调整 request 和 limit
3. **使用 HPA（Horizontal Pod Autoscaler）**：基于 CPU 使用率自动扩缩副本数
4. **定期审查**：监控 request 与实际使用的比例，避免过度分配或分配不足

## 5. 常见坑与故障排查

### 5.1 OOMKilled（内存超限被杀）

**现象：**
- Pod 状态显示 `OOMKilled`，容器重启次数增加
- `kubectl describe pod <name>` 中看到 `Reason: OOMKilled` 或 `Last State: Terminated`
- 内核日志：`Out of memory: Killed process xxx`

**原因：**
- 容器实际使用的内存超过了 `limits.memory`
- 内核 OOM killer 杀掉了容器内的进程（通常是 PID 1）
- 注意：Memory limit 是 **reactive enforcement**（反应式执行）——容器可能短暂超过 limit，但当内核检测到内存压力时才会杀进程

**解决：**
1. 提高 memory limit
2. 检查应用是否有内存泄漏
3. 使用 VPA 自动调整资源
4. 检查是否有 memory-backed emptyDir 占用了 memory limit 额度

**关键：** memory limit 不仅包含应用进程使用的内存，还包括：
- memory-backed emptyDir 卷（tmpfs）
- 容器可写层（如果使用 overlayfs）

### 5.2 CPU Throttling（CPU 限流）

**现象：**
- 应用延迟突增、响应时间 P99 飙高
- 容器 CPU 使用率看起来没到 limit，但性能仍然下降
- `kubectl top` 显示 CPU 使用率不高

**原因：**
- CPU limit 通过 CFS（Completely Fair Scheduler）quota 实现
- 默认 CFS 调度周期为 100ms，如果 limit=500m，容器在每 100ms 周期内最多用 50ms CPU 时间
- 如果容器在周期内前 50ms 就用完了配额，剩余 50ms 必须等待（throttle），即使 Node 上有空闲 CPU
- **关键坑：** 即使平均 CPU 使用率远低于 limit，瞬时突增（burst）仍可能被 throttle

**解决：**
1. **对延迟敏感的服务不设 CPU limit**（让容器能利用空闲 CPU），只设 request
2. 提高 CPU limit
3. 使用 Guaranteed QoS + static CPU 管理策略获得独占 CPU
4. 检查 CFS quota 周期设置（kubelet `--cpu-cfs-quota-period`）

### 5.3 调度失败（Pending）

**现象：** Pod 一直处于 `Pending` 状态，事件显示 `0/3 nodes are available: insufficient cpu/memory`

**原因：**
- 所有 Node 上已调度的 Pod request 之和 + 新 Pod 的 request 超过了 Node 容量
- 即使实际使用率低，调度器也只看 request

**解决：**
1. 降低 request 值（但要确保服务质量）
2. 增加节点
3. 检查是否有 Pod 过度 request（request 远高于实际使用）
4. 使用 VPA 推荐 request 值

### 5.4 Node-pressure Eviction（节点压力驱逐）

**现象：** Pod 被驱逐，状态变为 `Failed`，原因显示 `Evicted`

**触发条件：** kubelet 监控以下信号，达到阈值时驱逐 Pod：
- `memory.available`：节点可用内存不足
- `nodefs.available`：节点文件系统空间不足
- `nodefs.inodesFree`：inode 不足
- `imagefs.available`：镜像存储空间不足
- `pid.available`：PID 耗尽

**驱逐顺序：** BestEffort → Burstable（超过 request 的）→ Guaranteed

**默认硬驱逐阈值：**
```
memory.available < 100Mi
nodefs.available < 10%
imagefs.available < 15%
```

### 5.5 LimitRange 配置陷阱

**问题：** LimitRange 设的 default limit 小于用户手动指定的 request，导致 Pod 无法调度。

**示例：**
```yaml
# LimitRange 设了 default cpu limit = 500m
# 但用户 Pod 指定了 cpu request = 700m（无 limit）
# → LimitRange 自动注入 limit=500m，但 request=700m > limit=500m → 调度失败！
```

**解决：** 确保 LimitRange 的 default limit >= default request，或使用 ValidatingAdmissionPolicy 做更细粒度校验。

## 7. CPU vs Memory 行为对比

| 维度 | CPU | Memory |
|---|---|---|
| 资源类型 | 可压缩（compressible） | 不可压缩（incompressible） |
| 超过 limit 的后果 | Throttle（限流等待），不杀进程 | OOMKilled（杀进程） |
| 执行方式 | Proactive（主动限流） | Reactive（反应式，检测到压力才杀） |
| 能否临时超过 | 否，硬限制 | 可以短暂超过，但可能被杀 |
| 对 Pod 的影响 | 性能下降、延迟增加 | 容器被杀、重启 |
| 不设 limit 的风险 | 争抢其他容器 CPU | 可能 OOM 整个 Node |

## 8. 调试命令速查

```bash
# 查看 Pod 资源配置和 QoS 等级
kubectl describe pod <name> | grep -A5 -E "QoS|Limits|Requests"

# 查看 Pod 的 OOMKilled / 重启原因
kubectl describe pod <name> | grep -A10 "Last State"

# 实时资源使用
kubectl top pod <name>
kubectl top node

# 查看 Node 驱逐事件
kubectl get events --field-selector reason=Evicted

# 查看 Pod 的 resource request/limit（JSON 格式）
kubectl get pod <name> -o jsonpath='{.spec.containers[*].resources}'

# 检查 CPU throttling（需要 Node 上有 /sys/fs/cgroup 访问权限）
# CFS throttling 指标在 cgroup v2: /sys/fs/cgroup/cpu.stat
cat /sys/fs/cgroup/cpu.stat  # 查看 nr_throttled 和 throttled_time
```

### A1. 标准 Web 服务 Pod（Burstable）
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: web-app
spec:
  containers:
  - name: app
    image: myapp:v1
    resources:
      requests:
        cpu: "250m"
        memory: "256Mi"
      limits:
        cpu: "500m"
        memory: "512Mi"
```

### A2. 生产关键服务（Guaranteed + 独占 CPU）
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: critical-service
spec:
  containers:
  - name: app
    image: myapp:v1
    resources:
      requests:
        cpu: "2000m"     # 整数 CPU → static 策略可独占核
        memory: "4Gi"
      limits:
        cpu: "2000m"     # = request → Guaranteed
        memory: "4Gi"    # = request → Guaranteed
```

### A3. Namespace 资源管控（LimitRange + ResourceQuota）
```yaml
# LimitRange: 每个容器的默认值和边界
apiVersion: v1
kind: LimitRange
metadata:
  name: default-limits
  namespace: production
spec:
  limits:
  - default:
      cpu: "500m"
      memory: "512Mi"
    defaultRequest:
      cpu: "250m"
      memory: "256Mi"
    max:
      cpu: "4"
      memory: "8Gi"
    min:
      cpu: "50m"
      memory: "64Mi"
    type: Container
---
# ResourceQuota: 整个 Namespace 的总量限制
apiVersion: v1
kind: ResourceQuota
metadata:
  name: namespace-quota
  namespace: production
spec:
  hard:
    requests.cpu: "20"
    requests.memory: "40Gi"
    limits.cpu: "40"
    limits.memory: "80Gi"
    pods: "50"
```
